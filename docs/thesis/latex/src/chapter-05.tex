\chapter{Deployment and Execution}

This chapter describes how the implemented platform is executed in practice. The focus is operational rather than algorithmic: the goal is to show how the biomedical RAG service, scheduler, evaluation pipeline, vector store, relational database, and local language-model runtime are provisioned and coordinated during thesis execution. This matters because a reproducible thesis artifact is not only source code; it is also a concrete runtime environment whose service boundaries, infrastructure assumptions, and hardware profile influence what can be reproduced.

\section{Local-First Deployment Model}

Deployment is local-first and Compose-based~\cite{dockercompose2026docs}. The repository does not present the thesis system as a Kubernetes or Helm deployment. Instead, it uses containerized local services and file-based configuration so that the complete runtime can be inspected and reproduced on a workstation. This choice supports thesis transparency: the reader can trace which service is responsible for vector indexing, answer generation, audit persistence, or evaluation scoring without relying on opaque orchestration layers.
% evidence: ../engineering-wiki/wiki/repo-profiles/rag.md
% evidence: biomed_knowledge_platform/docker-compose.yaml
% evidence: llm_server/docker-compose.yml

The tradeoff is deliberate. A local-first deployment is easier to audit and adapt for research work, but it does not by itself imply production-grade orchestration, autoscaling, or high-availability guarantees. In this thesis, deployment is part of the research artifact: it defines the operational setting in which the platform was executed and evaluated, rather than claiming a production deployment architecture.

\section{Biomedical RAG Runtime Stack}

The biomedical RAG service runs as a separate application service alongside Qdrant and PostgreSQL. Qdrant stores vectorized document chunks and retrieval payloads~\cite{qdrant2026collections}, while PostgreSQL stores audit and relational application state~\cite{postgresql2026docs}. The FastAPI application exposes ingestion, retrieval, synthesis, and document-management endpoints and mounts its configuration files read-only so that runtime assumptions remain externalized and inspectable.
% evidence: biomed_knowledge_platform/docker-compose.yaml
% evidence: biomed_knowledge_platform/src/biomed_platform/api/app.py
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/qdrant/vector_index.py

This deployment layout mirrors the architectural separation described earlier. The application service does not embed vector storage internally, and the scheduler does not write directly to the vector store. Instead, cross-component communication occurs through explicit HTTP contracts and service boundaries. Operationally, this means that document indexing, vector search, relational auditing, and answer generation can be inspected as interacting subsystems rather than as hidden internal side effects.

\section{Local Language-Model Serving Stack}

The language-model runtime is deployed separately from the biomedical RAG service. The repository contains a dedicated local stack built around Ollama~\cite{ollama2026api}, with Open WebUI and Traefik used for local interaction and routing. This separation keeps model-hosting concerns outside the application code: the biomedical RAG service consumes LLM inference through HTTP, while model download, local storage, and process lifecycle remain deployment concerns of the LLM stack itself.
% evidence: llm_server/docker-compose.yml
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/ollama/ollama_client.py

This design has methodological value. By treating local model serving as an external dependency, the thesis can distinguish application-level behavior from model-hosting behavior. It also means that operational reproducibility depends not only on prompts and application code, but also on which local model artifact, quantization, and endpoint configuration were active when the benchmark was run.

\section{Scheduler and Evaluation Execution}

The PubMed scheduler executes as a separate acquisition subsystem. Its runtime configuration records scheduled UTC execution times and the API paths used to communicate with the biomedical RAG service. Operationally, this means acquisition timing, DOI resolution, and downstream ingestion coordination are executed independently of user query handling. The scheduler can therefore update the corpus continuously without requiring the answer-serving service to own acquisition logic directly.
% evidence: scheduler_pubmed/config/pubmed_scheduler.yaml
% evidence: scheduler_pubmed/src/core/use_cases/scheduler.py

The evaluation subsystem is executed as a command-line pipeline rather than as a long-running service. It reads configuration profiles, calls the RAG API and Ollama endpoints, materializes intermediate artifacts, and writes configuration snapshots into run directories. This execution model is appropriate for benchmark work because it makes every phase inspectable and replayable under a recorded configuration, while keeping evaluation logic outside the online request path.

\section{CUDA-Enabled Evaluation Execution}

The repository also supports a CUDA-oriented execution profile for the evaluation-side embedding workload used during RAGAS scoring. In the branch \texttt{cuda-validation-metrics}, commit \texttt{a1faf166} introduced a workstation-oriented configuration in which the evaluation profiles switch the \texttt{ragas.embeddings\_device} setting from \texttt{cpu} to \texttt{cuda} and align the dependent service endpoints with localhost execution. Conceptually, this is an execution-environment change for the evaluator rather than a change to the metric definitions or to the scientific interpretation of those metrics.

This distinction matters because the thesis does not present a blanket GPU migration of every subsystem. The verified CUDA path accelerates the evaluation-side sentence-transformer workload used during automated scoring, while retrieval, indexing, and answer synthesis remain separately configured in the biomedical RAG service. CUDA support is therefore part of the deployment and execution story, not evidence that all archived benchmark runs were executed on the same hardware path.

\section{Operational Boundaries and Reproducibility}

Deployment transparency improves reproducibility, but it does not guarantee identical reruns. Exact replay can still depend on local Qdrant state, local Ollama model files, service uptime, PubMed availability, and the specific benchmark artifact bundle selected for re-analysis. The deployment model therefore supports controlled execution and traceability rather than perfect future replay.
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260605_123942_nogit/config_snapshot.json
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/evaluation.logs

Two boundaries are especially important. First, a configuration file can document how a system may be run, but it does not prove which path was active in a canonical benchmark unless run artifacts confirm it. Second, operational changes such as moving evaluator embeddings from CPU to CUDA can alter execution cost and feasibility without changing the scientific meaning of the recorded metric artifacts. For this reason, deployment evidence in the thesis is tied to explicit configuration snapshots and documented runtime bundles rather than to assumptions drawn only from repository file presence.
