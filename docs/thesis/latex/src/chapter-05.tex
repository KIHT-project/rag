\section{Study Design}

This chapter defines the methodological protocol used to connect system construction with evaluable evidence. The study design does not treat the platform solely as a retrieval service; instead, it examines a composite workflow in which automated acquisition, manual abstract review, ingestion control, and experimental evaluation contribute different forms of validity. This framing is necessary because system quality depends not only on retrieval metrics, but also on whether the indexed corpus can be curated in a traceable and reproducible manner.

Methodologically, the architecture supports a staged form of validation. Automated services provide acquisition, indexing, and answer generation behavior, while the human curation workflow supplies manually reviewed task records that can be exported, enriched, and selectively handed to downstream ingestion. The design decision is to separate curation from online retrieval so that review judgments and metadata-completeness checks refine the evidence base without being conflated with query-time behavior. This supports clearer interpretation of later evaluation outcomes, although it does not by itself constitute clinical validation.

\section{Dataset Protocol}

The dataset protocol combines two complementary sources of evidence. First, biomedical documents enter the platform through scheduler-driven or direct ingestion workflows. Second, an annotation-oriented curation stream prepares abstract-level tasks for manual biomedical review. In the task-preparation stage, the workflow reads a structured Excel source, checks that required bibliographic columns are present, normalizes selected boolean review flags, optionally applies exclusion-oriented filters, and emits task payloads containing PMID, title, and abstract content.

After export from the curation workflow, the reviewed task set is enriched with DOI and related source metadata and then partitioned into separate artifact classes. The repository contains raw exported tasks, a clean dataset prepared for ingestion, a rejected-task report, and a file listing source identifiers for unresolved DOI enrichment cases. In the current artifact snapshot, 1300 tasks are present in the raw export, 1288 are retained in the clean export, and 12 are listed as rejected due to missing ingest-critical metadata. This partitioning supports reproducibility because later ingestion and evaluation steps can be tied to explicit intermediate datasets rather than reconstructed retrospectively.

\section{Annotation-Based Validation}

Annotation-based validation is used here as a curation and evidence-screening mechanism rather than as an experimental endpoint with claimed clinical outcomes. Exported reviewed tasks retain manual annotation objects together with the underlying abstract text and enriched document identifiers. The observed task structure includes review signals such as inclusion evidence spans, relation-to-venous-thrombosis choices, confidence ratings, risk-factor reporting choices, article-type choices, and category selections. These annotations provide structured human judgments that can be inspected alongside the indexed source records.

The methodological role of these curated tasks is twofold. First, they create a traceable bridge between manual screening activity and the subset of records eligible for RAG ingestion. Second, they provide a review-oriented substrate that can support later evaluation design, for example by identifying papers considered related to thrombosis or likely to contain risk-factor evidence. However, the current repository evidence does not establish inter-annotator agreement, annotation completeness guarantees, or a clinical adjudication protocol. Those limitations must therefore be preserved explicitly when interpreting any downstream findings.

\section{Reproducibility Protocol}

Reproducibility is supported through the project's repository-aware Engineering Wiki philosophy, configuration-driven execution, and durable intermediate artifacts. The curation workflow derives its behavior from environment variables controlling project identifiers, sheet selection, filter activation, export destinations, ingestion batch size, timeout values, and retry parameters. The export and ingestion stages both materialize inspectable files or request batches, which makes it possible to reconstruct which reviewed records were eligible for downstream import and which were excluded.

This repository-aware protocol improves methodological transparency by preserving raw, clean, rejected, and missing-identifier artifacts as separate states in the curation lifecycle. Evaluation runs also preserve configuration snapshots, which supports traceability between metric outputs and the settings used during execution. These mechanisms improve reproducibility at the data-processing and artifact-audit levels, but they do not guarantee byte-identical future behavior because model runtime state, vector-store state, and corpus state may change. The main limitation is that some workflow assumptions remain external to the code, including the operational practice by which reviewers complete annotations before export. Consequently, certain governance properties of the review process still require procedural documentation beyond the repository.

\section{Evaluation Protocol}

The current evaluation protocol uses 25 thrombosis oriented questions for answer generation. Each question is evaluated under three modes: LLM only, RAG without HyDE, and RAG with HyDE. The deterministic primary condition uses seed 42 and temperature 0.0, while a robustness group records five nominal seed settings at temperature 0.2. 

The evaluation is conducted using a phase-separated pipeline that materializes intermediate artifacts to ensure traceability and reproducibility. This approach separates the assessment of retrieval ranking from the assessment of answer quality and factor extraction. Seeds are used so that repeated runs can separate random variation from architectural behavior. In simple terms, a seed fixes the random starting point used by the model when temperature is above zero. If two runs use the same prompt, same model, same temperature, and same seed, they should follow the same stochastic path more closely than runs with different seeds. For a non-technical reader, this can be understood like shuffling a deck of cards with a numbered shuffle recipe: using the same recipe reproduces the same order, while changing the recipe can change the order. This is why the deterministic benchmark fixes seed 42 and why the robustness group repeats the experiment across seeds 11, 22, 33, 44, and 55.

Extraction evaluation is conditional on the availability of derived gold factors from the curated annotation substrate. Under the configured no-gold policy, queries without derived reference factors are skipped rather than counted as failures. This produces a query coverage rate of 0.52 and means that extraction results describe only the covered subset.

This distinction is central to the methodology: the thesis evaluates a research prototype and its measurement pipeline, not clinical safety or diagnostic correctness.
