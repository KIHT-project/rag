\section{Repository Structure Overview}

This appendix summarizes the repository structure that supports the thesis claims. The repository is organized as a monorepo because the thesis artifact, service implementation, evaluation framework, local model infrastructure, and curation tooling must remain inspectable together. This organization improves reproducibility: architectural claims can be checked against implementation modules, and evaluation claims can be checked against generated artifacts.
% evidence: ../engineering-wiki/wiki/repo-profiles/rag.md
% evidence: docs/thesis/STYLE_GUIDE.md

\begin{lstlisting}[caption={Repository-level module layout.}]
rag/
  biomed_knowledge_platform/   # FastAPI biomedical RAG service
  scheduler_pubmed/            # PubMed acquisition scheduler
  evaluation_metrics/          # Phase-based benchmark pipeline
  llm_server/                  # Ollama local model-serving stack
  labelstudio-tools/           # Label Studio curation utilities
  docs/thesis/latex/           # Thesis source and generated PDF
  docs/thesis/evidence/        # Artifact and claim registry
\end{lstlisting}

The biomedical RAG service follows a Clean Architecture and ports-and-adapters structure. Transport concerns live in the API layer, orchestration lives in use cases, domain models and ports remain framework-independent, and infrastructure integrations are implemented as adapters. This separation is visible in the service package layout and is central to the thesis argument that retrieval, ingestion, generation, and audit behavior can be reasoned about separately.
% evidence: biomed_knowledge_platform/src/biomed_platform/api/app.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/ports/ingestion.py
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/qdrant/vector_index.py
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/ollama/ollama_client.py

\begin{lstlisting}[caption={Biomedical RAG service package boundaries.}]
biomed_platform/
  api/        # routers, endpoint schemas, error handlers
  core/       # domains, use cases, ports, retrieval services
  adapters/   # Qdrant, Ollama, PubMed clients
  db/         # SQLAlchemy engine, models, Alembic integration
  audit/      # PostgreSQL-backed audit service
  common/     # settings, logging, middleware, utilities
\end{lstlisting}

The scheduler and evaluation modules follow the same repository philosophy. The scheduler owns PubMed acquisition and downstream ingestion coordination, while the evaluation subsystem owns benchmark execution and artifact generation. Neither subsystem directly mutates the internals of the other. This separation supports architectural transparency and avoids embedding benchmark-specific logic into the online service.

% evidence: scheduler_pubmed/src/adapters/rag/documents_client.py
% evidence: evaluation_metrics/src/eval_cli.py

\section{Configuration Architecture}

Configuration is deliberately externalized. The platform uses YAML files for service configuration and evaluation configuration, while Label Studio tooling uses environment variables for curation-specific secrets and runtime paths. This is consistent with the Engineering Wiki guidance to keep configuration explicit and avoid hidden runtime state.
% evidence: ../engineering-wiki/wiki/configuration/yaml-configuration.md
% evidence: biomed_knowledge_platform/src/biomed_platform/common/settings.py
% evidence: scheduler_pubmed/src/common/settings.py
% evidence: labelstudio-tools/src/app/python/config.py

\subsection{Retrieval Configuration}

The RAG configuration records the embedding provider, device, chunking strategy, vector backend, and default retrieval depth. These values affect both system behavior and evaluation interpretation because they define the embedding space, chunk granularity, and candidate pool size used before reranking and answer synthesis.
% evidence: biomed_knowledge_platform/configs/rag.yaml

\begin{lstlisting}[language={},caption={Representative retrieval configuration.}]
rag:
  embedding:
    provider: "sentence-transformers/all-MiniLM-L6-v2"
    device: "cpu"
    normalize_embeddings: false
  chunking:
    chunk_size: 1200
    overlap: 150
  vector_index:
    backend: "qdrant"
  retrieval:
    top_k: 10
\end{lstlisting}

\subsection{Vector Store Configuration}

The Qdrant configuration records the local endpoint, timeout, collection prefix, and distance metric. Collection names are derived from the configured prefix and embedding model identifier, which supports model-specific vector collections while preserving a stable service contract.
% evidence: biomed_knowledge_platform/configs/qdrant.yaml
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/qdrant/vector_index.py

\begin{lstlisting}[language={},caption={Representative Qdrant configuration.}]
qdrant:
  url: "http://localhost:6333"
  timeout_seconds: 30.0
  collection:
    name_prefix: "docs"
    distance: "COSINE"
\end{lstlisting}

\subsection{LLM Configuration}

The LLM configuration records the Ollama endpoint, generation model, HyDE model, prompt and context bounds, concurrency, retry count, and timeout. These values are important for reproducibility because the same retrieval contexts can produce different operational behavior when model identity, timeout, concurrency, or generation options change.
% evidence: biomed_knowledge_platform/configs/llm.yaml

\begin{lstlisting}[language={},caption={Representative LLM configuration.}]
ollama_base_url: "http://192.168.2.3:11434"
generator_model_id: "llama3.1:8b-instruct-q4_K_M"
hyde_enabled: false
ask_max_context_chars: 60000
ask_max_chunks_candidate: 30
ask_max_chunks_final: 6
llm_max_concurrency: 2
\end{lstlisting}

\section{Deployment and Infrastructure}

Deployment is local-first and Compose-based. The Engineering Wiki identifies Docker Compose as the verified local dependency mechanism for this repository; there are no verified Helm or Kubernetes deployment files for the current thesis implementation. This local-first design supports thesis reproducibility and inspection, but it also means the deployment should not be described as production-grade orchestration.
% evidence: ../engineering-wiki/wiki/repo-profiles/rag.md
% evidence: ../engineering-wiki/wiki/platform/docker-compose.md

The biomedical RAG stack defines Qdrant, PostgreSQL, and the API service as separate Compose services. Qdrant persists vectors in a named volume, PostgreSQL persists relational state in a named volume, and the API mounts configuration files read-only. This separation mirrors the application architecture: vector retrieval, relational state, and application behavior are independently configurable infrastructure concerns.
% evidence: biomed_knowledge_platform/docker-compose.yaml

\begin{lstlisting}[language={},caption={Representative biomedical RAG Compose services.}]
services:
  qdrant:
    image: qdrant/qdrant:v1.16.3
    ports: ["6333:6333", "6334:6334"]
  postgres:
    image: postgres:17.7
    ports: ["5432:5432"]
  api:
    build: .
    ports: ["8000:8000"]
    volumes:
      - ./configs:/service/configs:ro
\end{lstlisting}

The LLM stack is separate from the biomedical RAG service. It contains Ollama for model serving, Open WebUI for local interaction, and Traefik for local routing. This separation lets the RAG service treat LLM inference as an HTTP dependency while keeping model-hosting lifecycle concerns outside the application code.
% evidence: llm_server/docker-compose.yml
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/ollama/ollama_client.py

\begin{lstlisting}[language={},caption={Representative local LLM Compose services.}]
services:
  ollama:
    build: ./ollama
    volumes:
      - ollama_models:/root/.ollama
  open-webui:
    image: ghcr.io/open-webui/open-webui:0.6.43

\section{Evaluation Pipeline Details}

The evaluation subsystem is implemented as a command-line pipeline with explicit phases. Its purpose is to make evaluation outputs inspectable rather than transient. The same run directory stores configuration snapshots, generated answer records, RAGAS outputs, extraction summaries, and aggregate benchmark summaries.
% evidence: evaluation_metrics/src/eval_cli.py
% evidence: evaluation_metrics/src/utils/output_writer.py

\subsection{Retrieval Evaluation Workflow}

The retrieval evaluation code supports pool generation, BEIR-style metric computation, overlap auditing, and weak-label retrieval evaluation. In the canonical thesis run, however, phase 1 and phase 2 retrieval artifacts are not present. This is why Chapters 7 through 9 treat numeric retrieval ranking quality as an unresolved evidence gap rather than reporting invented nDCG or retrieval precision values.

\subsection{Generation and RAGAS Workflow}

Generation evaluation produces one answer file per mode: LLM-only, RAG without HyDE, and RAG with HyDE. For RAG modes, the evaluation records contexts extracted from the ask response rather than from a separate search call. This matters because faithfulness must be evaluated against the evidence actually supplied to the synthesis stage.
% evidence: evaluation_metrics/src/phases/phase3_generate.py
% evidence: evaluation_metrics/src/phases/phase4_ragas.py

\begin{lstlisting}[language={},caption={Canonical answer output pattern.}]
primary_deterministic/
  phase3_answers_llm_only.jsonl
  phase3_answers_rag_no_hyde.jsonl
  phase3_answers_rag_hyde.jsonl
  phase4_ragas_phase3_answers_*.csv
\end{lstlisting}

\subsection{Extraction Evaluation Workflow}

Extraction evaluation compares predicted risk factors with a reference substrate derived from curated tasks and canonical factor matching. The configured policy includes confidence filtering, closed-set prediction behavior, and inclusion of summary and citation snippet signals. The resulting metrics are separate from RAGAS because risk-factor recovery is a domain-specific outcome that answer relevancy alone cannot capture.
% evidence: evaluation_metrics/config/eval.yaml
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

\subsection{Benchmark Execution Structure}

The canonical benchmark uses a deterministic primary run and a stochastic robustness group. The primary run fixes seed 42 and temperature 0.0. The robustness run uses five seeds at temperature 0.2. This structure supports artifact-level reproducibility and basic sensitivity analysis, while remaining limited by the small five-query benchmark.

\section{Reproducibility Notes}

Reproducibility in this repository is strongest at the artifact and configuration level. The Makefile builds the thesis with two pdflatex passes, and the evaluation CLI writes timestamped run directories with configuration snapshots. The canonical thesis run is registered in the evidence index, which gives later readers a fixed reference point for the evaluation chapter.
% evidence: Makefile
% evidence: evaluation_metrics/src/eval_cli.py
% evidence: docs/thesis/evidence/ARTIFACTS.md

Local LLM behavior remains a reproducibility constraint. The service uses a locally reachable Ollama endpoint and a quantized Llama model. Even with deterministic seeds in the evaluation configuration, exact rerun identity can still depend on model files, host hardware, Ollama version, concurrency, timeout behavior, and service state. The benchmark artifacts therefore support audit of the completed run, but they do not by themselves guarantee byte-identical future generations.
% evidence: biomed_knowledge_platform/configs/llm.yaml
% evidence: llm_server/ollama/llm-models.json
% evidence: evaluation_metrics/config/eval.yaml

Hardware and runtime dependencies also affect repeatability. Embeddings are configured for CPU execution, Qdrant and PostgreSQL persist local state through volumes, and the API uses in-memory ingestion queues and stores in the current composition. These are acceptable thesis-prototype choices, but they should be recorded when comparing new runs against the canonical run.
% evidence: biomed_knowledge_platform/configs/rag.yaml
% evidence: biomed_knowledge_platform/docker-compose.yaml
% evidence: biomed_knowledge_platform/src/biomed_platform/api/app.py

The high-level and low-level design material requested for inspection is present as PDF files at repository level, not as the requested directories. The appendix therefore does not infer internal text from missing directories. Future thesis revisions should either register these PDFs in the evidence index or restore directory-based design documentation if more granular source material is required.

\subsection{Observed Label Studio Export Structure}

The exported Label Studio tasks contain a top-level identifier and a \texttt{data} object holding the bibliographic payload. In the clean export, the \texttt{data} object includes at least \texttt{pmid}, \texttt{title}, \texttt{abstract}, \texttt{doi}, \texttt{doi\_url}, \texttt{source}, \texttt{source\_id}, \texttt{source\_url}, \texttt{year}, \texttt{journal}, and \texttt{authors}. Additional export metadata includes timestamps, labeling status, project information, and the full list of annotations attached to the task.
% evidence: labelstudio-tools/ls_data/tasks_raw.json
% evidence: labelstudio-tools/ls_data/tasks_clean.json

The observed artifact snapshot contains 1300 raw exported tasks, 1288 clean tasks, and 12 rejected tasks. All clean tasks are marked as labeled in the export metadata. Within the clean task file, 1277 tasks contain one annotation object and 11 tasks contain two annotation objects. The evaluation code currently reads the first annotation object for a task, so this export shape should be treated as an implementation assumption rather than as proof of adjudicated multi-reviewer consensus.
% evidence: labelstudio-tools/ls_data/tasks_raw.json
% evidence: labelstudio-tools/ls_data/tasks_clean.json
% evidence: labelstudio-tools/ls_data/tasks_rejected.json
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

Within the observed annotations, the \texttt{result} array stores heterogeneous review items. These include span labels over abstract text, binary choices for relation to venous thrombosis and risk-factor reporting, confidence ratings, article-type choices, and clinical category selections. The repository supports an annotation model that combines inclusion rationale, topical relevance, confidence, and coarse categorization, but it does not prove that every task contains identical annotation content.
% evidence: labelstudio-tools/ls_data/tasks_raw.json

For downstream ingestion, the pipeline applies a stricter validity schema than the raw export format. A task is ingestion-ready only when it contains non-empty source metadata, DOI, year, journal, authors, title, and abstract fields. Tasks failing these checks are written to a rejected-task report, and unresolved identifier cases are tracked separately. This means that the RAG handoff assumes metadata completeness, while annotation completeness remains a procedural expectation outside the current code-enforced contract.

% evidence: labelstudio-tools/ls_data/tasks_rejected.json

\subsection{Operational Caveats}

The current ingestion runtime uses one worker, a small in-memory queue, in-memory job and idempotency stores, and bounded backpressure. This design is transparent and sufficient for local experiments, but it is not durable across process restarts. Production-oriented work would require durable queues, persistent job-state recovery, and corpus versioning before large-scale evaluation claims could be made.
% evidence: biomed_knowledge_platform/src/biomed_platform/api/app.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/services/ingestion/in_memory_queue.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/services/ingestion/backpressure.py

\subsection{Dependency Limitations}

PubMed acquisition depends on upstream response structure, DOI availability, and publication-date parsing. The scheduler records success, failure, and partial-success outcomes, but missing DOI metadata or inconsistent publication dates can reduce acquisition coverage. Similarly, vector retrieval depends on Qdrant availability and on the configured embedding model; generation depends on the local Ollama service.

\subsection{Scalability and Extensibility}

The repository structure supports future extension through ports and adapters. Embedding providers, vector storage behavior, PubMed clients, LLM clients, and evaluation phases can be replaced or extended behind existing boundaries. The current scalability constraints are therefore primarily operational rather than structural: durable ingestion state, corpus versioning, larger benchmark datasets, vector-store snapshots, and model-runtime provenance remain the key missing pieces for stronger future claims.
