\section{Repository Structure Overview}

This appendix summarizes the repository structure that supports the thesis claims. The repository is organized as a monorepo because the thesis artifact, service implementation, evaluation framework, local model infrastructure, and curation tooling must remain inspectable together. This organization improves reproducibility: architectural claims can be checked against implementation modules, and evaluation claims can be checked against generated artifacts.
% evidence: ../engineering-wiki/wiki/repo-profiles/rag.md
% evidence: docs/thesis/STYLE_GUIDE.md

\begin{lstlisting}[caption={Repository-level module layout.}]
rag/
  biomed_knowledge_platform/   # FastAPI biomedical RAG service
  scheduler_pubmed/            # PubMed acquisition scheduler
  evaluation_metrics/          # Phase-based benchmark pipeline
  llm_server/                  # Ollama local model-serving stack
  labelstudio-tools/           # Label Studio curation utilities
  docs/thesis/latex/           # Thesis source and generated PDF
  docs/thesis/evidence/        # Artifact and claim registry
\end{lstlisting}

The biomedical RAG service follows a Clean Architecture and ports-and-adapters structure. Transport concerns live in the API layer, orchestration lives in use cases, domain models and ports remain framework-independent, and infrastructure integrations are implemented as adapters. This separation is visible in the service package layout and is central to the thesis argument that retrieval, ingestion, generation, and audit behavior can be reasoned about separately.
% evidence: biomed_knowledge_platform/src/biomed_platform/api/app.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/ports/ingestion.py
% evidence: biomed_knowledge_platform/src/biomed_platform/adapters/qdrant/vector_index.py

\begin{lstlisting}[caption={Biomedical RAG service package boundaries.}]
biomed_platform/
  api/        # routers, endpoint schemas, error handlers
  core/       # domains, use cases, ports, retrieval services
  adapters/   # Qdrant, Ollama, PubMed clients
  db/         # SQLAlchemy engine, models, Alembic integration
  audit/      # PostgreSQL-backed audit service
  common/     # settings, logging, middleware, utilities
\end{lstlisting}

The scheduler and evaluation modules follow the same repository philosophy. The scheduler owns PubMed acquisition and downstream ingestion coordination, while the evaluation subsystem owns benchmark execution and artifact generation. Neither subsystem directly mutates the internals of the other. This separation supports architectural transparency and avoids embedding benchmark-specific logic into the online service.

\section{Configuration Architecture}

Configuration is deliberately externalized. The platform uses YAML files for service configuration and evaluation configuration, while Label Studio tooling uses environment variables for curation-specific secrets and runtime paths. This is consistent with the Engineering Wiki guidance to keep configuration explicit and avoid hidden runtime state.

\subsection{Retrieval Configuration}

The RAG configuration records the embedding provider, device, chunking strategy, vector backend, and default retrieval depth. These values affect both system behavior and evaluation interpretation because they define the embedding space, chunk granularity, and candidate pool size used before reranking and answer synthesis.
% evidence: biomed_knowledge_platform/configs/rag.yaml

\begin{lstlisting}[language={},caption={Representative retrieval configuration.}]
rag:
  embedding:
    provider: "sentence-transformers/all-MiniLM-L6-v2"
    device: "cpu"
    normalize_embeddings: false
  chunking:
    chunk_size: 1200
    overlap: 150
  vector_index:
    backend: "qdrant"
  retrieval:
    top_k: 10
\end{lstlisting}

\section{Deployment and Infrastructure}

Deployment is local-first and Compose-based. The Engineering Wiki identifies Docker Compose as the verified local dependency mechanism for this repository; there are no verified Helm or Kubernetes deployment files for the current thesis implementation. This local-first design supports thesis reproducibility and inspection, but it also means the deployment should not be described as production-grade orchestration.
% evidence: ../engineering-wiki/wiki/repo-profiles/rag.md
% evidence: ../engineering-wiki/wiki/platform/docker-compose.md

The biomedical RAG stack defines Qdrant, PostgreSQL, and the API service as separate Compose services. Qdrant persists vectors in a named volume, PostgreSQL persists relational state in a named volume, and the API mounts configuration files read-only. This separation mirrors the application architecture: vector retrieval, relational state, and application behavior are independently configurable infrastructure concerns.

\section{Evaluation Pipeline Details}
\label{sec:appendix-eval-pipeline}

The evaluation subsystem is implemented as a command-line pipeline with explicit phases. Its purpose is to make evaluation outputs inspectable rather than transient. The current appendix separates two artifact groups because they represent different phases of the evidence: the finalized generation and extraction benchmark, and the finalized independent retrieval benchmark.
% evidence: evaluation_metrics/src/eval_cli.py
% evidence: evaluation_metrics/src/utils/output_writer.py

\subsection{Evaluation Pipeline Implementation}

The evaluation subsystem follows the phase-separated architecture defined in Table~\ref{tab:evaluation-phases} (Chapter~\ref{chap:methodology}). Each phase performs a specific task and materializes its output before the next phase begins. This design supports reproducibility by allowing each stage of the benchmark to be inspected and audited independently.

Artifacts flow sequentially through the pipeline. The retrieval benchmark (Phases 1 and 2) establishes the evidence-ranking quality of the system, while the generation benchmark (Phases 3, 4, and 6) evaluates the quality and correctness of the final synthesized answers. This section documents the specific directory structure and artifact names resulting from these phases.

\section{Reproducibility Notes}

Reproducibility in this repository is strongest at the artifact and configuration level. The Makefile builds the thesis with two pdflatex passes, and the evaluation CLI writes timestamped run directories with configuration snapshots. The canonical thesis runs are registered in the evidence index, which gives later readers fixed reference points for both the generation benchmark and the retrieval benchmark.
% evidence: Makefile
% evidence: evaluation_metrics/src/eval_cli.py
% evidence: docs/thesis/evidence/ARTIFACTS.md

Local LLM behavior remains a reproducibility constraint. The service uses a locally reachable Ollama endpoint and a quantized Llama model. Even with deterministic seeds in the evaluation configuration, exact rerun identity can still depend on model files, host hardware, Ollama version, concurrency, timeout behavior, and service state. The benchmark artifacts therefore support audit of the completed run, but they do not by themselves guarantee byte-identical future generations.

% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260605_123942_nogit/config_snapshot.json

Hardware and runtime dependencies also affect repeatability. The archived canonical benchmark used CPU-side evaluation embeddings, while the "cuda-validation-metrics" branch also documents a CUDA execution option for evaluation-side embeddings through commit \texttt{a1faf166}. Qdrant and PostgreSQL persist local state through volumes, and the API uses in-memory ingestion queues and stores in the current composition. These are acceptable thesis-prototype choices, but they should be recorded when comparing new runs against the canonical run.

\section{CUDA and APEX Preparation}

CUDA execution for the evaluation subsystem should be prepared as an environment-validation procedure rather than as an informal host assumption. The required checks are straightforward. First, verify NVIDIA driver availability with \texttt{nvidia-smi}. Second, verify that the CUDA toolkit is available on the workstation and matches the intended runtime toolchain. Third, verify that the active PyTorch environment detects CUDA correctly before running the evaluation pipeline.
% evidence: evaluation_metrics/config/eval.yaml
% evidence: evaluation_metrics/src/phases/phase4_ragas.py

\begin{lstlisting}[language=bash,caption={Minimal CUDA environment validation sequence.}]
nvidia-smi
nvcc --version
python -c "import torch; print(torch.cuda.is_available())"
\end{lstlisting}

APEX should be treated conditionally. The verified repository configuration for the thesis evaluation subsystem does not declare NVIDIA APEX as a mandatory dependency, so APEX should only be installed or validated if a local execution profile explicitly requires it. When APEX is required, it must be built against the same CUDA toolkit and the same PyTorch environment that will execute the evaluation pipeline; mixing a different CUDA or PyTorch build is a common cause of import and runtime failures.
% evidence: evaluation_metrics/requirements.txt
% evidence: evaluation_metrics/config/eval.yaml

A short troubleshooting rule is sufficient for most failures. If CUDA is visible to the host but not to PyTorch, the problem is usually an environment or binary compatibility mismatch. If APEX imports fail, undefined symbol errors or extension build errors should be treated first as a signal that APEX was compiled against a different CUDA or PyTorch installation than the one currently active. In that situation, the correct response is to rebuild or reinstall APEX inside the exact execution environment intended for the thesis run, rather than to treat the failure as a benchmark anomaly.

\subsection{Operational Caveats}

The current ingestion runtime uses one worker, a small in-memory queue, in-memory job and idempotency stores, and bounded backpressure. This design is transparent and sufficient for local experiments, but it is not durable across process restarts. Production-oriented work would require durable queues, persistent job-state recovery, and corpus versioning before large-scale evaluation claims could be made.
% evidence: biomed_knowledge_platform/src/biomed_platform/api/app.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/services/ingestion/in_memory_queue.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/services/ingestion/backpressure.py

The complete chained June execution ran from 2026-06-05 15:39:43.685 to 2026-06-07 02:12:18.683, for 34 hours, 32 minutes, and 35 seconds. The paper benchmark phase consumed 32 hours, 47 minutes, and 46 seconds, followed by 1 hour, 44 minutes, and 42 seconds for retrieval preparation. Phase 4 RAGAS evaluation consumed approximately 20 hours, 26 minutes, and 56 seconds, making it the dominant runtime bottleneck.
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/evaluation.logs

The same logs contain repeated warnings that the evaluator returned one generation instead of the requested three. RAGAS scoring completed successfully, but this evaluator behavior must be disclosed when interpreting the reported metrics. The logs also contain a Python 3.14 compatibility warning involving Pydantic V1 functionality; this is recorded here as an operational caveat rather than as a central scientific finding.
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/evaluation.logs

The nominal robustness runs should also be interpreted with care. The evaluation CLI passes seed and temperature controls to the direct Ollama call used by the LLM-only baseline. The current RAG API path does not expose equivalent request-level stochastic controls for synthesis or HyDE generation, and the RAG answers and contexts are identical across robustness seeds except for volatile identifiers. Zero variance in the RAG modes is therefore deterministic service behavior under the benchmark path, not evidence of stochastic robustness.

\subsection{Dependency Limitations}

PubMed acquisition depends on upstream response structure, DOI availability, and publication-date parsing. The scheduler records success, failure, and partial-success outcomes, but missing DOI metadata or inconsistent publication dates can reduce acquisition coverage. Similarly, vector retrieval depends on Qdrant availability and on the configured embedding model; generation depends on the local Ollama service.

\subsection{Scalability and Extensibility}

The repository structure supports future extension through ports and adapters. Embedding providers, vector storage behavior, PubMed clients, LLM clients, and evaluation phases can be replaced or extended behind existing boundaries. The current scalability constraints are therefore primarily operational rather than structural: durable ingestion state, corpus versioning, larger benchmark datasets, vector-store snapshots, and model-runtime provenance remain the key missing pieces for stronger future claims.
