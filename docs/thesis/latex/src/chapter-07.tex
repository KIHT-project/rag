\section{Experimental Setup}

This chapter evaluates the platform as a set of separable capabilities: retrieval preparation and ranking, answer generation, answer support, risk factor extraction, robustness behavior, and operational runtime. This separation is necessary because a configuration can retrieve useful evidence but synthesize a weak answer, or it can produce a relevant-looking answer without evidence grounding. The evaluation therefore avoids reducing the system to a single aggregate score.

The evaluation subsystem follows the phase-based approach described in Table~\ref{tab:evaluation-phases} (Chapter~\ref{chap:methodology}), ensuring that every metric can be traced back to its specific implementation phase and materialized artifact.

\section{How to Read the Metrics}

The evaluation uses several metric families because the platform performs several different tasks. A retrieval metric asks whether useful evidence appears near the top of a ranked list. A generation metric asks whether the answer is relevant to the question or supported by supplied contexts. An extraction metric asks whether the system recovered a set of risk factors. A runtime metric asks how expensive the benchmark was to execute. These metric families are related, but they are not interchangeable. A high retrieval score does not automatically imply a faithful answer, and a relevant answer does not automatically imply correct risk-factor extraction.
% evidence: evaluation_metrics/src/phases/phase4_ragas.py
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

All reported scalar metrics in this chapter are interpreted with their denominator in mind. A score of 0.80 usually means ``80 percent of the relevant measured behavior under this specific definition'', not ``80 percent clinically correct''. For example, Precision@5 counts only the top five retrieved items; micro F1 counts individual extracted factor decisions across covered queries; answer relevancy is an automated evaluator score over generated answers. Each value is therefore meaningful only when paired with its evaluation object, evidence source, and run snapshot.
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260605_123942_nogit/paper_benchmark_summary.json
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260606_212735_nogit/retrieval_metrics_summary.json

The simplest way to understand a metric is to ask what mistake it punishes. Precision punishes extra unsupported items. Recall punishes missed relevant items. F1 punishes imbalance between precision and recall. Faithfulness punishes answer statements that are not supported by the supplied contexts. Context precision without reference punishes contexts that appear less useful for supporting the generated answer. Latency punishes slow execution. This thesis reports these metrics separately so that the reader can see which kind of mistake each configuration tends to make.
% evidence: evaluation_metrics/src/phases/phase4_ragas.py
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

\section{Retrieval Evaluation}

Retrieval evaluation asks whether the system ranks relevant biomedical evidence near the top of the result list. This is different from asking whether the final answer is well written. A retrieval system can find relevant papers while the generator still writes a weak answer, and a generator can write a plausible answer even when retrieval was poor. The independent retrieval metrics therefore evaluate the ranked evidence list before answer synthesis. The independent retrieval metrics are computed during the evaluation phases: Candidate Pooling (Phase 1) and Retrieval Evaluation (Phase 2), which evaluate ranked document lists against manually annotated relevance judgments (Qrels).
% evidence: evaluation_metrics/README.md
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260606_212735_nogit/retrieval_metrics_summary.json

Precision at k measures how many of the top k returned items are relevant. If the system returns five papers and three are relevant, Precision@5 is 3/5, or 0.60. This metric is easy to interpret because it asks a concrete reviewer question: ``If I read the first five results, how many are useful?'' It does not ask whether all relevant papers in the corpus were found.

Recall at k measures how many of the known relevant items were recovered within the top k. If a query has four relevant papers in the annotated gold set and the system retrieves two of them in the top five, Recall@5 is 2/4, or 0.50. This metric asks a different reviewer question: ``How much of the known useful evidence did the system recover early?'' A system can have high precision but lower recall if it returns a small number of very good items while missing other relevant papers.

Mean Reciprocal Rank (MRR) measures how early the first relevant result appears. The reciprocal rank for a query is 1.0 when the first result is relevant, 0.5 when the first relevant result is second, and approximately 0.33 when it is third. MRR averages this value across queries. It is useful when the first useful result matters strongly, such as when a reviewer wants to see at least one relevant source immediately.

Normalized Discounted Cumulative Gain at k (nDCG@k) rewards rankings that place more useful documents earlier~\cite{jarvelin2002ndcg}. Unlike binary precision and recall, nDCG can incorporate graded relevance, so a highly relevant document at rank 1 is worth more than a weakly relevant document at rank 5. Intuitively, nDCG asks whether the ranking order is good, not just whether relevant items appear somewhere in the cutoff.

These four retrieval metrics should be read together. Precision@5 emphasizes top-five purity, Recall@5 emphasizes top-five coverage, MRR emphasizes the first useful hit, and nDCG@5 emphasizes graded ordering. No single retrieval metric captures all aspects of evidence ranking.

\subsection{Retrieval Ranking Results}

The finalized metrics show why retrieval interpretation must remain multidimensional. HyDE's higher MRR means the first relevant item tended to appear earlier. Its higher Recall@5 means more of the judged relevant evidence was recovered in the first five results. Direct retrieval's slightly higher Precision@5 means a slightly larger share of its top-five items were relevant, and its higher nDCG@5 means its ordering of weakly relevant and highly relevant documents was stronger at the same cutoff. The evidence therefore supports a tradeoff rather than a single winner: HyDE is stronger for early-hit discovery and coverage, while direct retrieval is stronger for top-five purity and graded ordering.

The interpretation of this result is that HyDE acts as an effective discovery mechanism—it is more likely to surface a relevant document even when the user query is slightly misaligned with the corpus terminology. However, direct retrieval remains the precision leader; when it finds relevant documents, it ranks them more accurately according to their graded relevance. For a biomedical researcher, this means HyDE is better for broad evidence gathering, while direct retrieval is more reliable for ranking known high-quality evidence.

\section{Generation and RAGAS Evaluation}

Generation quality is evaluated using Retrieval Augmented Generation Assessment (RAGAS) metrics~\cite{es2024ragas}. Answer relevancy estimates whether the response addresses the user's question. Faithfulness estimates whether the generated response is supported by supplied contexts. Context precision without reference estimates whether the retrieved contexts appear useful for supporting the produced answer without using a separate gold answer. It is an answer-support proxy, not an independent retrieval ranking metric and not proof of biomedical correctness. Answer Generation (Phase 3) and RAGAS Evaluation (Phase 4) provide the basis for evaluating answer quality and support.
% evidence: evaluation_metrics/src/phases/phase4_ragas.py

Answer relevancy can be understood as a question-answer alignment score. If the question asks about thrombosis risk factors and the answer discusses those risk factors directly, answer relevancy should be higher. If the answer drifts into unrelated background material, answer relevancy should be lower. This metric is useful for detecting whether the response addresses the prompt, but it does not require the answer to cite or obey retrieved evidence. For that reason, the LLM-only baseline can receive an answer relevancy score even though it has no retrieved contexts.
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260605_123942_nogit/primary_deterministic/phase4_ragas_phase3_answers_llm_only.jsonl

Faithfulness measures a different property. It asks whether statements in a generated answer are supported by the contexts supplied to the generator. In simple terms, if the context says ``factor A is associated with thrombosis'' and the answer says ``factor A is associated with thrombosis'', that statement is supportable. If the answer adds a factor or causal claim that is not present in the supplied context, faithfulness should decrease. Faithfulness is therefore central to evidence-grounded RAG evaluation, but it is not applicable to the LLM-only baseline because no retrieved contexts are supplied.
% evidence: evaluation_metrics/src/phases/phase4_ragas.py

Context precision without reference is more subtle. It estimates whether the contexts supplied to the answer appear useful for supporting the answer, without comparing the contexts to an independent gold answer. A high value can indicate that the answer is focused around the retrieved material. However, it is not the same as Precision@5 from retrieval evaluation. Precision@5 requires manual relevance judgments over ranked retrieved documents; context precision without reference is an automated answer-support proxy computed during RAGAS evaluation. This distinction remains important even after retrieval finalization because the RAGAS metric evaluates answer support, whereas the finalized June 2026 retrieval benchmark evaluates document ranking against qrels.

\section{Risk Factor Extraction Evaluation}

Risk factor extraction is evaluated separately from general answer quality. The extraction phase compares predicted risk factor sets with derived gold factors from curated task annotations and cited documents. Risk factor extraction is evaluated in Extraction Evaluation (Phase 6), which compares system-extracted factors against the derived reference substrate. True positives count correctly recovered factors, false positives count predicted factors absent from the derived reference set, and false negatives count derived reference factors missed by the system. Precision captures over-extraction, recall captures missed factors, and F1 balances the two.
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

A true positive is a correctly recovered risk factor. If the derived reference set contains ``prior venous thromboembolism'' and the system extracts the same canonical factor, that is a true positive. A false positive is an extra factor predicted by the system but not present in the derived reference set. A false negative is a derived reference factor that the system failed to extract. These counts are the raw building blocks of precision, recall, and F1.
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

Precision asks, ``When the system extracts a factor, how often is that extraction in the reference set?'' If a system extracts 10 factors and 7 are correct, precision is 7/10, or 0.70. Low precision means the system creates too many unsupported extractions, which increases human review burden. Recall asks, ``Of the factors that should have been extracted, how many did the system find?'' If the reference set contains 8 factors and the system finds 6, recall is 6/8, or 0.75. Low recall means the system misses known factors. F1 combines precision and recall so that a system is penalized when one is high and the other is low.
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

Micro and macro averaging answer different aggregation questions. Micro precision, recall, and F1 pool all individual factor decisions across the covered queries before computing the metric. This means queries with more factors can have more influence. Macro precision, recall, and F1 compute per-query scores first and then average them, giving each covered query more equal influence. Reporting both views makes the extraction result less dependent on a single aggregation convention.

\section{Robustness Interpretation}

The robustness group should not be interpreted as evidence that the RAG modes demonstrated stochastic stability. Inspection of the Phase 3 (Answer Generation) code shows that the evaluation CLI passes temperature and seed to the direct Ollama call used by the LLM-only baseline. The RAG API calls do not receive equivalent request-level stochastic controls. Inspection of the ask path shows that RAG synthesis and HyDE generation receive service-controlled defaults; the synthesis path uses deterministic options, and the HyDE path uses deterministic options with caching.

\section{Threats to Validity}

The first threat is benchmark size. The answer-generation benchmark contains 25 questions. These size is appropriate for inspecting the research prototype, but is not supporting broad statistical or clinical claims.
% evidence: evaluation_metrics/queries/queries.jsonl
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260605_123942_nogit/paper_benchmark_summary.json

The second threat is reference construction. Extraction gold factors are derived from curated tasks, confidence policy, cited DOI alignment, and canonical factor matching. This substrate is reproducible, but it is not an adjudicated clinical gold standard.
% evidence: evaluation_metrics/runs/old/june-07-valid-full-run-25-queries/20260605_123942_nogit/config_snapshot.json
% evidence: evaluation_metrics/src/phases/phase6_extraction.py

The third threat is stochastic-control validity. Robustness seed and temperature controls currently propagate to the LLM-only direct Ollama call, but not equivalently to the RAG API path. Zero variance in RAG robustness outputs should therefore not be interpreted as stochastic robustness.
% evidence: evaluation_metrics/src/phases/phase3_generate.py
% evidence: biomed_knowledge_platform/src/biomed_platform/core/use_cases/ask.py

The fourth threat is evaluator behavior. RAGAS scoring depends on evaluator model behavior and produced repeated warnings that one generation was returned where three were requested. The metrics remain useful as recorded benchmark artifacts, but this limitation affects confidence in automated evaluator stability.

\section{Evaluation Synthesis}

The evaluation demonstrate that the platform achieves its goal of a traceable, multi-phase biomedical RAG benchmark. The results establish that system performance is not uniform across different tasks.

\begin{itemize}
    \item \textbf{Retrieval Performance:} HyDE is superior for early-hit discovery (MRR) and coverage (Recall), making it suitable for broader literature search. Direct retrieval is superior for top-K purity (Precision) and graded ordering (nDCG), making it better for specific evidence ranking.
    \item \textbf{Generation Quality:} Direct RAG is significantly more faithful (68.6\%) than HyDE-enabled RAG (48.1\%). While HyDE produces answers that appear more focused according to automated support proxies, it increases the risk of ungrounded synthesis.
    \item \textbf{Extraction Accuracy:} Direct RAG is the more reliable configuration for risk factor extraction, achieving a Micro F1 of 0.745 compared to 0.723 for HyDE. Both configurations struggle with a high false-positive rate, indicating that the synthesis stage is prone to over-identifying factors.
    \item \textbf{Operational Cost:} Automated evaluation is the dominant bottleneck, with RAGAS scoring consuming over 20 hours of the 34-hour execution. This highlights the trade-off between exhaustive automated measurement and rapid development cycles.
\end{itemize}

Ultimately, the platform provides a defensible foundation for biomedical research by making these trade-offs visible. The strongest configuration depends on whether the user prioritizes finding at least one relevant source (HyDE) or ensuring that the synthesized answer is strictly supported by evidence (Direct RAG).
